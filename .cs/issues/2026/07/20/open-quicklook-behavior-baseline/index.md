# QuickLook 现有行为基线与兼容性矩阵

## 探索问题与停止条件

- 要支持的理解或决策：解释用户在 Windows 文件界面按下空格后，QuickLook 如何识别上下文、取得选择、匹配插件并显示结果；明确 Rust Broker、WPF Legacy Host 和 Preview Protocol 必须保留的行为。
- 本轮边界：实现基线固定为 QuickLook `4.5.0`（提交 `b13df028f3cce1f84792f7043b57bf5cea3a3e4c`）；已完成的静态路径证据来自 `master` 快照 `bca2fd4e863b8d9aef0d0d518837846a274c2b9a`，用于识别发布后的差异和候选修复，不自动进入实现。本机 `4.1.1` 及用户插件只承担向后兼容运行基线。
- 什么状态算足够行动：主路径、关键兼容分支、插件生命周期和位数边界有直接证据；运行时未知被转成可执行矩阵；结果足以约束 Broker 和协议 issue。

## 一句话模型

全局键盘钩子把有效窗口中的空格转换为预览命令，窗口管理器通过按位数编译的原生 Shell 适配取得当前选择，再由按优先级加载的 WPF 插件准备并填充预览窗口。

## 探索边界

- 已覆盖：启动和单实例、键盘触发、命令分发、Shell 选择、第三方文件管理器分支、插件发现/匹配、WPF 内容契约、取消和故障回退的源码路径。
- 明确不展开：每个文件格式的解码实现、视觉样式细节、安装/更新、商店发布、Rust 未来实现方案的具体类型和代码。
- 仍然未知：现有版本真实的冷/热延迟、空闲资源、快速切换竞态、插件崩溃表现、32 位文件对话框的运行与失败行为和第三方插件样本兼容性；ARM64 证据保留供未来事项，不属于本轮交付边界。

## 当前结论

源码直接表明 QuickLook 的主链路由常驻监听、低级键盘钩子、命令分发、Shell 选择、插件匹配和 WPF Viewer 共同完成。键盘事件只在受支持的前台窗口或 QuickLook 自身窗口中转成命令；当前选择由 C++/COM 层按窗口类型分派；插件通过反射加载，按优先级串行执行 `CanHandle`，随后创建新实例并通过 `Prepare`、`View`、`Cleanup` 操作 WPF 上下文。

这意味着 Rust Broker 可以接管热键、窗口识别、选择获取和会话治理，但不能在保持二进制插件兼容的同时直接替代 WPF 插件宿主。`4.5.0` 的位数边界也已经收窄：主程序在 x64 Windows 上作为 x64 进程运行，唯一有直接证据必须匹配 x86 的路径是传统 32 位文件对话框钩子；它由独立 Win32 helper 桥接，不要求另一套 x86 Broker、Viewer 或插件宿主。现有第三方文件管理器适配使用窗口消息或应用 IPC，尚无必须匹配位数的证据。

本机安装的 QuickLook `4.1.1` 已提供第一批运行证据：Windows 11 x64 上的第二实例命令能够对文本、Markdown 和 PE 样本完成 3/3 打开与关闭；Explorer 选中文件后空格到可见窗口的 4 个有效样本为 `96-174 ms`，中位数约 `165 ms`；主进程同时加载了 18 个内置插件目录和 17 个用户插件程序集。CLI 测得的约 `1.72-1.80 s` 明显不代表空格预览延迟，内容首帧仍未单独观测。实现行为以 `4.5.0` 为准，`4.1.1` 只验证向后兼容，`master` 中的变化必须作为独立修复验证，三者不能直接互相外推。

## 与具体变化的关系

- 必须修改：把热键/选择/命令的唯一归属移动到 Broker；在 WPF 侧增加版本化命令入口；为插件宿主建立独立进程生命周期；保留插件优先级、准备、查看和清理语义；把现有 Native32/WoW64 helper 收拢为由 Broker 监督的 x86 Dialog Adapter。
- 需要验证：空格按下/释放语义、快速切换时旧操作取消、Explorer 搜索框排除、桌面、x64/x86 文件对话框、第三方管理器选择、固定窗口和焦点丢失。
- 仍待调查：除传统文件对话框外是否还有必须保留匹配位数辅助组件的适配；Legacy Host 失败后的可接受视觉降级；真实第三方插件集合。ARM64 原生依赖与格式覆盖留在未来独立事项。

## 用户修正与已排除理解

- “纯 Rust 完全替换 WPF 是目标”：用户确认 WPF Viewer/Legacy Host 长期保留，该理解已排除。
- “现有第三方插件可以不兼容”：用户确认插件兼容性是硬约束，该理解已排除。
- “必须 clean-room 重建插件契约”：用户确认 `PreviewIt` 采用 QuickLook GPLv3 派生路线，该理解已排除；Legacy Host 和 QuickLook.Common 可以直接复用。
- “直接以当前 `master` 开始实现”：用户确认采用稳定版 `4.5.0` 的固定提交作为源码基线；`master` 只提供经独立验证的候选修复，本机 `4.1.1` 和 17 个用户插件程序集作为向后兼容样本。
- “支持 x86 意味着发布另一套完整应用”：用户确认首版只发布 x64 主架构且不支持 32 位 Windows；唯一 x86 组件是受 Broker 监督的 Dialog Adapter，用于保留 32 位传统文件对话框选择能力。
- “ARM64 应随首版一起交付”：用户确认 ARM64 排除在本 Epic 和首版之外；相关上游代码与原生依赖证据只作为未来独立事项的输入。
- “使用 Rust 会自然获得完整故障隔离”：已排除；隔离来自进程边界、超时和恢复协议，不仅来自语言。

## 待确认问题

- x86 Dialog Adapter 的运行基线仍待补：需要在真实 32 位文件对话框中验证选择结果、启动耗时、超时、异常退出和 Broker 恢复。
- 第三方插件样本已从本机用户插件目录取得 17 个真实程序集；仍需固定插件清单、版本和代表性预览文件，才能执行可复现的二进制兼容测试。
- 性能目标如何定：已有 `4.1.1` 暖态 CLI 端到端数据，但仍需干净启动、Explorer 空格、内容首帧和快速切换的分段测量。
